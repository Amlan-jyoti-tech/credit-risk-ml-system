# Phase 0.6: Temporal Dataset Design & Validation

## 1. Overview

This document confirms the construction of the final temporal datasets for the credit-risk prediction system. It verifies that the temporal splitting strategy established in P0.4 and P0.5 produces valid, non-overlapping cohorts that adhere to strict leakage prevention protocols.

| Attribute | Decision |
| :--- | :--- |
| **Data Source** | `data/processed/lending_club_target_cleaned.parquet` |
| **Train Set** | Issue years 2007–2014 |
| **Validation Set** | Issue year 2015, 36-month term only |
| **Test Set** | Issue year 2016, 36-month term only |
| **Prediction Point** | Loan Origination |

No active/current loans remain. The minimum issue date is Apr-2008 and the maximum is Sep-2016, confirming proper temporal boundaries.

## 4. Preprocessing Fit Protocol (Leakage Prevention)

The `FeatureEngineer` class was strictly **fit on the Train dataset only**. Validation and Test sets were transformed using only parameters learned from the training data.

### 4.1 Learned Capping Thresholds (99.5th Percentile)
Outlier caps were learned on Train and correctly applied across all splits:
*   `annual_inc`: **$300,000** (Any income above this is capped)
*   `dti`: **36.27** (The 999 sentinel values and extremes are securely capped)

### 4.2 Learned Informative Missingness (Max + 1)
For the 5 informative-missingness delinquency fields, the `null` imputation value was learned as `max(train) + 1` for Logistic Regression:
*   `mths_since_last_delinq`: **189.0**
*   `mths_since_last_record`: **130.0**
*   `mths_since_last_major_derog`: **189.0**
*   `mths_since_recent_bc_dlq`: **171.0**
*   `mths_since_recent_revol_delinq`: **181.0**

*(Note: For XGBoost, the explicit value `-1` was used to ensure trees can easily split missing values aside).*

### 4.3 Upper Bounds Audit (`revol_util` and `bc_util`)
*   **Train `revol_util` > 100%:** 1,218 rows (max 892.3%)
*   **Train `bc_util` > 100%:** 7,807 rows (max 339.6%)
> [!NOTE]
> These values exceed 100%, which usually signifies a borrower exceeding their credit limit. While capping them at 100% loses the nuance of "over-limit" behavior, the affected rows represent $\approx 0.2\%$ and $\approx 1.7\%$ of the training set respectively. We have preserved the 100% hard cap defined in P0.5, but flag it here as a minor candidate for relaxation in later iterations if model calibration is struggling.
